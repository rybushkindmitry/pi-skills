# Скилл `auditing-architecture-projections` — дизайн

Статус: на утверждении
Дата: 2026-11-18

## Зачем

У большинства репозиториев архитектурные проекции (разрезы) не оформлены не
потому, что архитектуры нет, а потому что её покрытие никто не проверяет.
Скилл делает аудит любого репозитория по фиксированному списку проекций,
выдаёт вердикт с доказательствами, по запросу записывает карту покрытия в
репо и по явному вызову генерирует скелеты недостающих проекций.

## Цели

1. **Аудит** (всегда): оценить репо по 11 проекциям — verdict
   `covered` / `partial` / `gap` на каждую, с доказательством
   (`файл:строка` или пометка `inferred` из кода/конфига).
2. **Карта** (по явному запросу человека): записать
   `docs/architecture-coverage.md` — матрица «проекция → статус →
   доказательство → куда идти за подробностями», коммитится в git,
   показывает динамику между проверками.
3. **Закрытие пробелов** (отдельный явный вызов): для выбранных проекций
   сгенерировать скелеты документов по конвенциям скилла
   `structuring-repo-documentation` (ADR для решений,
   `architecture-current.md` для текущего состояния). Никогда не пишем
   в репо без явного разрешения.

## Не-цели

- Не оценивать *качество* архитектуры (хорошая/плохая) — только покрытие
  проекций.
- Не строить C4-диаграммы.
- Не навязывать arc42/C4 как обязательный формат — рамки дают списки
  признаков, а не требования к документам.
- Read-only по умолчанию: любая запись в репо — только по явному
  разрешению человека в диалоге.

## Правила честности вердикта

- Каждый вердикт требует цитаты `файл:строка` либо пометки `inferred` —
  когда проекция покрыта кодом/конфигом, но не документирована
  (например, `deploy/` закрывает «Развёртывание»).
- «Нет упоминаний в docs/» ≠ автоматически `gap`: сначала проверяется
  покрытие кодом, конфигом и инфраструктурными файлами.
- Шкала: `covered` / `partial` / `gap` + пометка `inferred`.

## Процесс скилла

1. **Инвентаризация**: README, docs/, adr/, deploy/, инфраструктурные
   файлы, структура кода; при наличии — graphify-граф и pi-lens
   (module/project report) как источники доказательств.
2. **Вердикты**: по каждой проекции — статус + доказательство.
3. **Отчёт в чат**: таблица «проекция → статус → доказательство», список
   пробелов с приоритетом (какой пробел опаснее других).
4. **Карта** (по запросу): запись `docs/architecture-coverage.md`.
5. **Fill** (по явному вызову): скелеты выбранных недостающих проекций;
   при наличии принятых решений — предложение оформить ADR.

## Структура

```
skills/auditing-architecture-projections/
  SKILL.md                     # триггеры, процесс, правила честности
  references/projections.md    # 11 проекций: вопрос, где искать, признаки covered/partial
  references/fill-mode.md      # как генерировать скелеты, связка со structuring-repo-documentation
```

## Где живёт

Репо `rybushkindmitry/pi-skills` (`skills/…`) — pi подхватывает скиллы из
`~/.pi/agent/git/…` автоматически, отдельная установка не нужна.

## Подходы (рассмотренные)

- **Три отдельных скилла** (аудит / карта / fill) — отклонено: три точки
  входа, дублирование списка проекций.
- **Один скилл, только аудит** — отклонено: цикл «нашёл → починил»
  разорван, пробелы так и остаются пробелами.
- **Один скилл, три режима** (выбрано): одна точка входа, общий список
  проекций, запись в репо — только по явному разрешению.

## Остаётся билдеру

- Точные эвристики признаков по каждой из 11 проекций.
- Формат таблицы отчёта и формат `architecture-coverage.md`.
- Имена аргументов вызова (фокус-проекции, режим fill).
- Решение, делать ли большой репо через сабагентов.
