# 11 проекций: вопросы и эвристики детекции

Источник для таблицы отчёта SKILL.md. Имена проекций дословно отсюда.

Набор строк у каждой проекции свой — не у всех все. В строках
«Inferred → вердикт» указано, к какому вердикту обычно ведёт такое
доказательство в коде/конфиге.

Шкала вердиктов и пометки `documented`/`inferred` — в SKILL.md, раздел
«Вердикты».

## 1. Контекст

- **Вопрос:** что за система, кто её окружает — пользователи, внешние
  системы, границы.
- **Где искать:** README, `docs/*.md`, концепт-доки, диаграммы контекста.
- **Covered:** назначение, основные акторы и внешние системы названы и
  связаны с системой.
- **Partial:** назначение есть, но границы/внешние системы не названы.
- **Частая ошибка:** путать с маркетинговым описанием; нужен именно круг
  «кто с кем взаимодействует».

## 2. Декомпозиция

- **Вопрос:** из каких блоков/модулей состоит сервис и за что каждый
  отвечает.
- **Где искать:** README «как устроено», `docs/architecture*.md`, карта
  каталогов `src/`, `graphify-out/`.
- **Covered:** есть карта блоков с обязанностями и границами.
- **Partial:** блоки можно перечислить только по структуре каталогов.
- **Inferred → partial:** дерево каталогов + именование модулей (`api.py`,
  `engine.py`) — код-уровень, до covered не дотягивает.

## 3. Runtime-схема

- **Вопрос:** как блоки взаимодействуют во времени: потоки обработки,
  последовательности, состояния сущностей, конкурентность.
- **Где искать:** концепт-доки, схемы потоков, state machine в коде,
  определения маршрутов/пайплайнов (DSL, YAML-роуты).
- **Covered:** поток основной обработки описан; если есть сущности с
  жизненным циклом — их состояния и переходы.
- **Partial:** поток восстановим только чтением диспетчера/оркестратора.
- **Inferred → covered:** DSL-маршруты + таблица переходов в коде
  (декларативный артефакт).

## 4. Данные

- **Вопрос:** модель данных, где хранится, кто владеет, миграции, потоки.
- **Где искать:** ER-доки, схема storage, миграции, ORM-модели, описание
  форматов состояния.
- **Covered:** сущности, хранилище и владение описаны; миграции очерчены.
- **Partial:** модель видна только в коде моделей/схем.
- **Частая ошибка:** «нет ER-диаграммы» ≠ gap, если сущности и хранилище
  однозначно видны из кода/конфига.

## 5. Интеграции

- **Вопрос:** контракты с внешними системами: API, ошибки, повторы,
  идемпотентность.
- **Где искать:** код API-клиентов, `docs/` интеграций, OpenAPI/контракты,
  вебхуки.
- **Covered:** список внешних систем и контракты взаимодействия названы.
- **Partial:** интеграции видны только по коду клиентов.
- **Inferred → partial:** код клиентов без описания контрактов;
  конфиг-описания интеграций → covered.

## 6. Развёртывание

- **Вопрос:** топология: серверы, процессы, порты, окружения, конфиги,
  секреты.
- **Где искать:** `deploy/`, docker-compose, Dockerfile, systemd-юниты,
  k8s-манифесты, CI/CD-файлы, раздел install в README.
- **Covered:** понятно, как система развёрнута и куда смотреть за деталями.
- **Partial:** команды запуска есть, топология/окружения не описаны.
- **Частая ошибка:** это самый частый ложный gap — инфра-файлы почти всегда
  закрывают проекцию без единого документа.

## 7. Отказы

- **Вопрос:** что ломается и как система деградирует: таймауты, retry,
  recover, ограничения.
- **Где искать:** guards/retry/recovery в коде, `docs/` надёжности,
  лимиты в конфигах, обработка крахов процесса.
- **Covered:** сценарии деградации названы и обеспечены механизмом.
- **Partial:** точечные механизмы (retry где-то) без общей картины.
- **Inferred → covered:** политики как данные (лимиты/таймауты/повторы в
  конфиге); разрозненный retry в коде → partial.

## 8. Безопасность

- **Вопрос:** границы доверия, аутентификация/авторизация, секреты,
  изоляция.
- **Где искать:** auth в коде/конфиге, handling секретов, изоляция
  процессов/контейнеров, `docs/` безопасности, threat model.
- **Covered:** authn/authz, работа с секретами и изоляция названы и
  обеспечены.
- **Partial:** меры есть, границы доверия не очерчены.
- **Частая ошибка:** сводная threat model — nice-to-have; её отсутствие не
  делает проекцию gap, если меры видимы.

## 9. Наблюдаемость

- **Вопрос:** как видно, что происходит внутри: логи, метрики, аудит,
  health.
- **Где искать:** логирование и метрики в коде, health-эндпоинты,
  дашборды/алерты, `docs/` эксплуатации.
- **Covered:** каналы наблюдаемости названы и работают (метрики/логи/health).
- **Partial:** только логи или только метрики; нет свода.
- **Inferred → partial:** модуль метрик + эндпоинт; полный набор
  (метрики + логи + health) → covered.

## 10. NFR

- **Вопрос:** качественные атрибуты и чем обеспечены: производительность,
  ёмкость, стоимость, лимиты.
- **Где искать:** `docs/` качества, лимиты/бюджеты в конфигах, нагрузочные
  тесты, ADR с NFR.
- **Covered:** атрибуты названы, у каждого есть обеспечивающее решение.
- **Partial:** отдельные лимиты в конфигах без свода атрибутов.
- **Частая ошибка:** это самый частый честный gap; не растягивать на
  «отсутствует идеальный мониторинг производительности».

## 11. Эволюция

- **Вопрос:** как система меняется: ADR, точки расширения, границы ядра,
  миграции, roadmap.
- **Где искать:** `docs/adr/`, CHANGELOG, roadmap-доки, plugin-структура,
  границы ядра/расширений.
- **Covered:** принятые решения журналируются; точки расширения названы.
- **Partial:** решения приняты, но не журналируются (или наоборот).
- **Частая ошибка:** отсутствие ADR при наличии другого журнала решений
  (specs с датировками) — partial, не gap.
