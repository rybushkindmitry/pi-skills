# Auditing architecture projections

Оценка репозитория по 11 фиксированным архитектурным проекциям: по каждой —
вердикт `covered` / `partial` / `gap` с доказательством. Аудит read-only;
запись в репозиторий (карта покрытия, скелеты документов) — только после
явного «да» человека.

Core principle: **аудит — это фиксированный список проекций и доказательства,
а не свободное эссе.** Отчёты двух разных репозиториев (или двух прогонов по
одному) должны быть сравнимы строка в строку.

## Процесс

### 1. Загрузить список проекций

Прочитай `references/projections.md` — он же лежит рядом с этим SKILL.md.
Там ровно 11 проекций с вопросами и эвристиками детекции. Таблица отчёта —
ровно эти 11 строк, имена дословно из справочника. Свои разрезы в таблицу не
добавлять; ценные наблюдения вне списка — в отдельную секцию «Вне списка».

### 2. Инвентаризация доказательств

Собрать материал, не вынося вердиктов: README, `docs/` (включая
`docs/adr/`, `docs/specs/`), `deploy/` в корне репо, инфраструктурные файлы
(docker/compose/systemd/k8s/CI), конфиги, структура кода. Если в репо есть
`graphify-out/graph.json` — использовать как карту модулей и сообществ.
Если доступны инструменты pi-lens (`project_report`, `module_report`) —
использовать как источник структуры модулей.

### 3. Верификация документарных доказательств

Каждый планируемый `covered (documented)` проходит спот-чек: 1–3 фальсифицируемых
утверждения из цитируемого документа сверяются с кодом или декларативными
артефактами. Приоритет: (а) ссылки на файлы и тесты — существуют ли они;
(b) именованные идентификаторы (функции, env-переменные, proto-поля);
(c) утверждения, датированные до последнего крупного рефакторинга репо.
Проверка grep-уровня — полная сверка не требуется. Сбор кодовых цитат «в
дополнение к доку» верификацией не считается: проверяется то, что док
**утверждает**, а не ищется подтверждение рядом.

- Все проверенные утверждения подтвердились → пометка `documented, verified`.
- Часть не подтвердилась → это **дрейф документации**: фиксируется в «Вне
  списка»; вердикт пересматривается по выжившим доказательствам (проекция
  может остаться covered — по другому доказательству), но пометка `verified`
  не ставится.
- Не подтвердилось ничего → вердикт по общим правилам (partial/gap).
- Сверить нечего (концептуальное утверждение без следов в коде) → пометка
  остаётся `documented`.

Верификация — проверка качества доказательства, а не качества документации
или архитектуры: она не меняет шкалу вердиктов и не оценивает «хорошо ли
написан док».

### 4. Вердикты

Для каждой из 11 проекций вынести вердикт по шкале:

| Вердикт | Значение |
|---|---|
| `covered` | Проекция отражена документом **или** однозначно восстановима из декларативных артефактов (конфиг, DSL, схема, инфра-файлы) без чтения императивного кода |
| `partial` | Отражена фрагментарно либо восстановима только чтением кода |
| `gap` | Не отражена нигде: ни документом, ни очевидным артефактом |

Структура каталогов и именование модулей — это код, а не декларативный
артефакт: если блоки восстановимы только из них, вердикт
`partial (inferred)`, не `covered`. `covered (inferred)` — только конфиг,
DSL, схема, инфра-файлы.

К каждому вердикту — пометка происхождения доказательства:

- `documented` — есть документ: цитата `файл:строка`;
- `inferred` — доказательство в коде/конфиге: цитата `файл:строка` и одна
  строка, что именно там доказывает проекцию.

Пометка одна на вердикт: если доказательство есть и в документе, и в коде —
помечай `documented` и цитируй документ; вердикты, прошедшие спот-чек (§3),
получают пометку `documented, verified`. Для `gap` пометки нет: в колонке
«Доказательство» ставится «—».

Монорепо с радикально разными сервисами — одна таблица на сервис; в
заголовке отчёта имя сервиса.

«Нет упоминаний в docs/» — **не** повод для `gap`: сначала проверить код,
конфиг и инфраструктурные файлы (`deploy/` закрывает развёртывание, CI-файлы
закрывают часть pipeline и т.п.). `gap` ставится, только если проекция не
видна нигде.

### 5. Отчёт

Формат отчёта фиксирован; обязательные секции: таблица, «Пробелы», «Что
дальше», «Вне списка» (у пустой «Вне списка» заголовок всё равно присутствует):

```markdown
## Архитектурный аудит <repo>

| # | Проекция | Вердикт | Доказательство |
|---|----------|---------|----------------|
| 1 | Контекст | covered (documented, verified) | README.md:3 — назначение и внешние системы |
| … | … | gap | — |
| … | … | … | … |

Итог: N covered, M partial, K gap.

## Пробелы (по убыванию риска)
1. <проекция> — чем опасен пробел именно этому репо, один-два абзаца…

## Что дальше
- Карта покрытия: могу записать `docs/architecture-coverage.md` (срез + таблица) — скажи, если нужно.
- Закрытие пробелов: могу сгенерировать скелеты выбранных проекций — назови, какие.

## Вне списка (наблюдения)
<заметные архивные наблюдения, не попавшие в 11 проекций; секция может быть пустой. Найденный дрейф документации (неподтвердившиеся утверждения доков) обязателен здесь>
```

В секцию «Пробелы» входят и `gap`, и `partial`; fill применим к обеим.
Риск пробела оценивать по этому репо: чем больше людей/клиентов/изменений
опирается на проекцию, тем дороже её отсутствие. Не оценивать *качество*
архитектуры — только покрытие: «плохо спроектировано» вне скилла.

### 6. Карта и fill — только по явному запросу

- **Карта.** После явного «да» записать `docs/architecture-coverage.md`:
  заголовок с датой среза, та же таблица вердиктов, секция «Пробелы».
  Карта хранит один — последний — срез; история срезов живёт в git-истории
  файла; «Вне списка» в карту не входит. Между аудитами карта не меняется:
  fill и скелеты её не трогают — вердикты пересматривает следующий аудит.
- **Fill.** Прочитать `references/fill-mode.md` и следовать ему.

## Read-only по умолчанию

Аудит ничего не пишет: ни карту, ни скелеты, ни правки существующих
документов. Запись — только после явного разрешения человека на этот
конкретный шаг. «Отчёт готов» ≠ «можно писать».

## Red flags

| Мысль | Реальность |
|---|---|
| «Для этого репо важен другой разрез, добавлю свой» | Список фиксирован — иначе отчёты несравнимы. Своё — в «Вне списка» |
| «В docs/ нет — значит gap» | Сначала код, конфиг, инфра-файлы. `deploy/` = развёртывание |
| «✅/⚠️ нагляднее, чем covered/partial/gap» | Только шкала скилла: она делает прогоны сравнимыми |
| «Доказательство очевидно, цитату можно опустить» | Вердикт без `файл:строка` или `inferred` — не вердикт, а мнение |
| «Док процитирован — значит доказан» | Цитата ≠ сверка: существование файлов/тестов/идентификаторов, на которые ссылается док, проверяется по коду (§3) |
| «Нашёл фантомную ссылку в доке — понижаю вердикт» | Дрейф документации ≠ отсутствие покрытия: дрейф — в «Вне списка», вердикт — по выжившим доказательствам |
| «Сейчас быстро допишу недостающий док» | Read-only: запись только после явного «да» на этот шаг |
| «Проекция покрыта, но код плохой — отмечу gap» | Качество кода вне аудита: покрытие есть — вердикт covered |
| «Скелет с TODO создан — проекция закрыта» | Скелет не меняет вердикт; его пересматривает следующий аудит |

## Common mistakes

- Оценка «как оформлена документация» вместо «какие проекции закрыты»:
  уродливый, но полный ответ на вопрос проекции — это covered.
- «Я читал код рядом с доком, значит сверил»: собрать кодовые цитаты — не то
  же, что проверить утверждения дока — фантомные тесты/файлы проходят мимо.
- Пробелы без привязки к репо («стоит добавить наблюдаемость» везде одинаково):
  риск должен быть аргументирован этим проектом.
- Fill-режим с выдуманным содержимым: скелет — это TODO-плейсхолдеры и
  факты из аудита с цитатами, ничего больше.
