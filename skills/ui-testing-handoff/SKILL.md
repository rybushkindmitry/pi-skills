# UI-Testing Handoff

## Overview

UI готов к передаче, когда закрыты три независимых вопроса, и ни один из них
не подменяется другим:

1. **Контракт** — экран читает ровно то, что бэкенд сериализует.
2. **Состояния** — ни один элемент управления не односторонний и не «липкий».
3. **Полный цикл на реальной машине** — оба направления работы проверены на
   целевой ОС, а не только в эмуляции.

Пирамида автотестов и CI-матрица — хорошо, но их недостаточно: они не ловят
расхождение контракта, односторонние механики и поведение на целевой машине.
Закрывают это четыре специализированные практики ниже — плюс обязательный
клик-проход владельцем по матрице покрытия.

| Слой | Средство | Кто выполняет |
|---|---|---|
| Логика бэкенда | юнит- и сквозные тесты движка | разработчик (TDD) |
| Контракт бэкенд↔фронт | контрактный тест сериализации | разработчик |
| Поведение экранов | сценарные тесты (jsdom + fake API/timers/promises) | разработчик |
| Матрица покрытия UI | `docs/ui-coverage.md`: элемент → имя теста или ручной шаг | разработчик, обновляется при каждом хотфиксе |
| Полный цикл | E2E-стенд с синтетическими ловушками, оба направления | разработчик/QA |
| Целевая машина | дым: запуск, скриншот, ключевые экраны | автоматика + владелец |
| Приёмка | клик-проход владельцем по матрице покрытия | владелец |

## 1. Контрактные фикстуры — из реальной сериализации

Самый дорогой класс UI-багов: тесты закрепили воображаемую форму данных, а
бэкенд сериализует иначе. Симптом — колонки/поля экрана показывают
`undefined` в реальном приложении, хотя все тесты зелёные.

- Фикстуры фронтенд-тестов строятся ТОЛЬКО из фактической сериализации:
  сверяйся с эталоном типов (сгенерированные биндинги, `models.ts`), а не с
  Go/TS-именами структур.
- Обязателен контрактный тест на стороне бэкенда: `json.Marshal` ключевых
  ответов (то, что уходит на экран) ассертит конкретные ключи, которые читает
  фронтенд, — включая вложенные структуры (имена на верхнем уровне и теги на
  вложенных могут расходиться).
- Границы регистрируй в тест-комментарии: правило «читаем только
  сериализованные ключи» должно быть видно следующим.

Ловушка: если одно поле сериализуется с тегом, а соседнее без — фиксируй оба
варианта в контрактном тесте. Частичная миграция тегов — типичный источник.

## 2. Матрица покрытия UI

Файл `docs/ui-coverage.md`: таблица по экранам, каждая строка —
«элемент/поведение → имя автотеста (vitest `describe/it`) ИЛИ пункт ручной
проверки владельца с шагами и ожидаемым результатом».

- Каждая строка ссылается на РЕАЛЬНОЕ имя теста — выдуманных имён нет
  (проверяется поиском по тестовым файлам).
- Пробелы честны: скролл/виртуализация в реальном WebView, фокус, поведение
  на 50+ МБ — «ручная проверка владельцем», не притворяются автотестом.
- Матрица обновляется при каждом хотфиксе: новый хотфикс — новая строка и
  актуальный счётчик кейсов.
- Клик-проход владельцем идёт ТОЛЬКО по матрице: это формальный слой приёмки,
  а не свободное исследование (свободное исследование — отдельно и после).

## 3. Аудит «липких» и односторонних состояний

Линза аудита: «однажды установил — нельзя снять», «установил — переживёт
смену контекста», «состояние по умолчанию опаснее альтернативы».

Чек-лист по каждому элементу управления:

- **Односторонние выборы.** Радиокнопки и select'ы: есть ли путь ВЕРНУТЬСЯ к
  пустому/нейтральному значению? (HTML-radio повторным кликом не снимается —
  нужен явный механизм: тоггл по повторному клику, «пустая» опция или кнопка
  очистки.)
- **Тумблеры, переживают смену контекста.** Пользовательские флаги
  («оставить как есть», «показать всё») сохраняются при загрузке нового
  документа/файла? Безопасное значение по умолчанию — то, при котором ничего
  не пропускается; при смене контекста сбрасывай в безопасную сторону.
- **Режимы, зависящие друг от друга.** Элемент A блокируется состоянием
  элемента B — что происходит с уже выбранным значением A при смене B?
  (Должно: сбрасываться явно и синхронно в DOM, а не только в модели.)
- **«Проснувшийся автопилот».** Есть автоподстановка значения? Ручной выбор
  пользователя должен блокировать её навсегда (в пределах контекста) — флаг
  «трогали вручную»; и сбрасываться вместе с контекстом.

Сценарии-тесты этого семейства (jsdom + fake timers + управляемые обещания):

- изменение во время ВЫПОЛНЯЮЩЕГОСЯ первого запроса не теряется: pending-
  повтор после завершения, ровно один, с новой разметкой;
- повтор из `finally` не гасит индикатор процесса раньше времени — счётчик
  глубины, скрытие только при нуле;
- двойной клик не создаёт параллельных вызовов (управляемое обещание:
  первый не разрешён, второй клик — вызов один);
- разблокировка кнопок в `finally`, в том числе на ошибке;
- сброс тумблеров при смене файла — DOM-чекбоксы синхронны с состоянием.

## 4. E2E-стенд: оба направления, ловушки, детерминизм

Для приложений «документ → обработка → документ» (анонимизация→восстанов-
ление, конвертация, миграция) уровень E2E — отдельный консольный стенд,
использующий те же пакеты, что и UI, без пере-имплементации логики:

- **Оба направления + промежуточная правка.** Цикл: прямое преобразование →
  имитация внешней правки (реформат значений, добавленные/переставленные
  строки) → обратное преобразование → поячеечная сверка с исходником
  (значения И типы/форматы). Асsert'ы на то, что должно было измениться и на
  то, что должно остаться нетронутым.
- **Синтетические ловушки в фикстурах:** скрытые строки/столбцы/листы,
  колонтитулы и комментарии с персональными данными, «пустые» листы, значения-
  обманки («не указан», «—»), значения в форматах, которые правила
  заведомо не распознают (проба известного пропуска — ассерт фиксирует и
  пропуск, и корректную замену после ручной разметки).
- **Связи через контекст:** один и тот же объект на разных листах/файлах —
  закрепи ожидаемое поведение тождества ассертом на РАЗЛИЧАЮЩЕМСЯ случае
  (не только на случае, где совпадение возможно случайно).
- **Детерминизм вывода.** Отчёт стенда — доказательство, значит вывод
  детерминирован: сортируй всё, что собирается из map/множеств; «отчёты
  идентичны» пишут только после `diff` двух прогонов. Тест на
  детерминизм (два прогона, байтовое сравнение) — обязательный.
- **Формулировки отчётов — доказуемые.** «Совпали счётчики и проверки» вместо
  «отчёты идентичны», если прогоны на разных машинах/версиях; цитаты значений
  — из фактических артефактов, не по памяти.

## 5. Дым на реальной машине без интерактивного доступа

Когда целевая машина — ВМ/удалённый стенд, а CI-раннера с этой ОС нет:

- Запуск GUI-приложения по SSH: `schtasks /Create /SC ONCE ... /IT` (флаг /IT
  обязателен — процесс в интерактивной сессии; SSH-запуск невидим), после
  проверки — снять задачу и завершить процесс.
- Проверка отрисовки: скриншот через гипервизор (`virsh screenshot <домен>`
  на хосте ВМ, через SSH-прыжок), скриншот скопировать обратно и смотреть.
- Первый кадр бывает чёрным (уснувший монитор/DPMS) — «разбудить»
  `virsh send-key <домен> KEY_LEFTSHIFT`, повторить скриншот.
- НЕ вводить клавиатуру, если в консоли ВМ открыта рабочая сессия
  пользователя — нажатия попадут в её окна. Только запуск/скриншот/уборка.
- Файлы стенда на целевой машине не удалять — владелец осматривает их.
- Бинарники перекладывать после КАЖДОГО изменения фронтенда: владелец тестирует
  то, что лежит на машине, а не то, что в репозитории.

## 6. Клик-проход владельцем

Финальный слой. Владелец проходит матрицу покрытия по строкам «ручная
проверка» на свежеразвернутом exe, с реальными (синтетическими) файлами.
Находки оформляются задачами; исправления — через обычный цикл; после
исправления exe разворачивается заново и проход повторяется по затронутым
строкам. До клик-прохода заявление «UI готов» не делается.

## Common mistakes

- Фикстуры фронтенд-тестов писать руками по Go/TS-именам → расхождение с
  сериализацией → зелёные тесты и сломанный экран.
- Ассерт «межконтекстного тождества» пинить только на совпадающем случае —
  он не различает корректную и сломанную реализацию.
- Оставлять пользовательский тумблер с безопасно-опасным значением включённым
  между документами.
- В отчёте стенда писать «вывод идентичен» при недетерминированном порядке
  строк (итерация Go-map).
- Считать CI-матрицу заменой дыма на целевой машине: матрица тестирует
  сборку, не развёртывание.
- Клик-проход «по ощущениям» вместо матрицы — находки не воспроизводимы,
  покрытие не измеримо.
